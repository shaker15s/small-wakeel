# R46 — «الوضعان»: السيستم السري + CLI-Anything الحقيقي

> الرؤية الكاملة للـ Round 46 — وكيل مش مجرد موك: موظف حقيقي بيبني نظامه الخاص
> (لللي مش عندهم نظام — وهم الأغلبية)، وبيتبنى عليه CLI حقيقي من CLI-Anything
> الحقيقي (لللي عندهم برنامج) — بإذن صاحب الشغل.

---

## ١. الوضع الأول — السيستم الداخلي السري (أولوية قصوى — الأغلبية)

### المبدأ
أغلب أصحاب الشغل مش عنداهم أي نظام — ورقة وقلم أو لا حاجة. **وكيل نفسه هو النظام**:
نظام داخلي كامل (أصناف، أطراف، أسعار، ديون، مواعيد، عادات شغل) بيتبني ويكبر يوم
بيوم من المحادثة — **بلا ما المستخدم يعرف إن فيه نظام أصلاً**.

### كيف يتحقق في الكود
| الطبقة | الآلية | المكان |
|---|---|---|
| التحويل الصامت | كل معلومة دائمة في كلام المستخدم (صنف/سعر/اسم/سياسة) → `memory_save` أو الأداة المناسبة فورًا — بصوت الموظف («أنا فاكرها») لا صوت الآلة | `prompt.ts` — قسم «النظام الداخلي» |
| شبكة العلاقات | الذاكرة مش جمل مبعثرة: صنف↔سعر↔مورد↔موعد — الـ 5-Layer Memory + Lexicon (entityRef) تربطها | `src/lib/agent/memory.ts` |
| الحوافز (hooks) | مواعيد تقرب → تذكير؛ صنف قارب يخلص → اقتراح شراء قبل النفاذ؛ عميل قاعد → اقتراح تواصل — بأولوية: فلوس > مخزون > فرصة > تذكير | `get_proactive_insights` + `radar.ts` |
| التعلم من التصحيح | تصحيح واحد = حقيقة جديدة أعلى درجة، من غير ما يتكرر مرتين | `memory-policy.ts` + WRITE-MEMORY-ON-LEARN |
| الصوت | «جاهز — البيعة اتسجلت بـ ٤٥٠ جنيه» — ممنوع إظهار الآلية (جداول/JSON/tools) | `prompt.ts` — صوت الموظف |

### ما الذي يمنع «الوك»
- **الموك** يكرر نفس الرد وسناريو مسجّل. الوكيل هنا: كل تصحيح يغير سلوكه،
  وكل يوم يضيف حوافز جديدة، وكل رقم جاي من السجل لا من التخيل.
- **الاختبار**: بطارية 1000+ سيناريو موظف حقيقي (R46 battery) عبر 4 أنشطة —
  أي سيناريو فيه رد جاهز/رقم مخترع/تجاهل تصحيح = فشل يُحسب.

## ٢. الوضع الثاني — CLI-Anything الحقيقي (هو نفسه — مش نسخة)

### المبدأ
لصاحب الشغل اللي عنده برنامج (دفتره، أمان، أي تطبيق): **لا نسخ ولا محاكاة** —
يُثبَّت CLI-Anything الحقيقي (`github.com/HKUDS/CLI-Anything`) على جهازه
**بإذنه الصريح**، فيبني هارنس CLI حقيقي لبرنامجه، ووكيل ينفذ عليه مهام كاملة
وحدها بسرعة CLI.

### السلسلة (كلها في الكود — `src/lib/agent/cli-anything/harness-installer.ts`)
```
طلب المستخدم «اربطلي دافتره»
        │
        ▼
cli_harness_install({app, confirmed:false})
        │  ← بطاقة إذن: بيوضح الأداة + البيئة + الخطوات (من غير تثبيت)
        ▼
المالك: «أيوة اعملها»
        ▼
cli_harness_install({app, confirmed:true})
        │
        ├─ pythonProbe() — هل يوجد Python 3.9+؟
        ├─ المسار A: hubSearch() → hubInstall()   (CLI-Hub — harnesses جاهزة)
        ├─ المسار B: generatePipeline(app, source) — الـ 7 phases على الكود الحقيقي
        │      P0 مصدر حقيقي (اسم program لوحده مرفوض — مبدأ CLI-Anything)
        │      P1 تحليل الكود (GUI actions → API calls)
        │      P2 تصميم CLI (مجموعات أوامر/حالات/صيغ إخراج)
        │      P3 تنفيذ (Click + REPL + --json + PEP-420 namespace)
        │      P4/P5 خطة اختبارات + unit/E2E
        │      P6 تشغيل الحزمة + توثيق النتائج
        │      P7 نشر (pip / PyPI cli-anything-<software>)
        │
        ▼
parseSkillMd(SKILL.md) — سطح الأوامر القابل للتنفيذ
        ▼
registerHarness() → جدول AppHarness (لكل منشأة)
        ▼
harnessesPromptBlock() — الدماغ «شايف» الهارنس في برومبته
        ▼
cli_control_app({app, command}) → execHarness() — الأمر الحقيقي --json
        على برنامج المالك نفسه (bridge.ts — الهارنس المتعلم يكسب السجل الثابت)
```

### بوابات الأمان
- **الإذن إلزامي**: `confirmed` لا يقبل `true` إلا بعد سؤال المالك صراحةً
  (برومبت الدماغ مأمور يسأل — و«الإذن» هو الكلمة التي تعيد الاستدعاء).
- **failing closed**: مفيش Python؟ → رسالة صريحة. مفيش في الـ hub؟ → يقترح
  المسار B مع المصدر. فشل تنفيذ؟ → الخطأ الحقيقي، لا بيانات مخيَّنة.
- **عزل لكل منشأة**: `@@unique([businessId, app])` — هارنسي منشأتين مش متشاركين.

## ٣. انضباط المهام (نمط Claude Code)
- **الخطة التزام لا زينة**: خطوة واحدة «في التنفيذ» في أي لحظة، الباقى ينتظرون.
- **الفور**: كل خطوة تخلص → تحديث حالتها فورًا — ممنوع تجميع التحديثات.
- **الغفلة فشل**: تجاوز خطوة في خطة متفق عليها = فشل شغل يُقال بصراحة.
- **صيغة المضارع** للخطوة الجارية («بُسجّل البيعة…») — والقائمة نفسها تعرض التقدم.

(مضغوط في `prompt.ts` — بروتوكول PLAN-FIRST + TASK DISCIPLINE.)

## ٤. بطارية 1000+ سيناريو (`tests/evals/`)
- **138** حالة مكتوبة يدويًا (أنماط مثبتة) + **952** حالة مولّدة
  (`case-generator.ts`): كل صنف × كل عميل × كل مورد × مبالغ بنظامي الأرقام
  (٠-٩ و 0-9) × صيغ مصرية حقيقية.
- **مشغّل متوازي** (pool=6) — 1090 حالة في ~7 دقائق لا ساعات.
- **حالات R46 الجديدة**: طلب ربط برامج (دفتره/أمان/أكسيل) — الرد يجب أن يكون
  صادقًا (إذن/توجيه/شرح)؛ تحصيل من عميل بلا دين → سؤال (عربون/سلفة) لا انهيار.
- **الشرط**: أي فشل = ثغرة منتج حقيقية (توجيه/تفسير/سلامة مال) — ليست «خطأ اختبار».

## ٥. ما الذي يُثبت أن الوكيل «أقوى من موظف بشري»
1. **لا ينسى**: تصحيح مرة واحدة = حقيقة دائمة (الذاكرة + الـ lexicon).
2. **لا يخطئ في المال**: كل حركة مال = مسودة + اعتماد + تحقق خادم
   (`operation-validation.ts` — لا كمية صفر، لا مبلغ غير صحيح، لا دفع فوق المستحق).
3. **يُتابع قبل السؤال**: حوافز (مواعيد/نفاذ/ديون) تروح للمالك قبل أن يصبح
   المشكلة مشكلة.
4. **يشغّل برامجه**: الوضع الثاني — مهام كاملة على برنامج المالك بإذن واحد.
5. **يُقاس**: 1090 سيناريو دوري — أي تدهور = فشل يُحسب قبل أن يشعر به المالك.

## ٦. حدود صريحة (شرف المهنة)
- في بيئة السحابة (مش جهاز المالك) لا يتصور الوكيل وصولًا لأجهزة خارجية —
  كل أمر يعود بحالة صريحة. لا «محاكاة نجاح».
- CLI-Anything يعمل من Python؛ بدون Python على الجهاز، الرسالة تقول ذلك.
- كل «نجاح» في الرد مقترن بتنفيذ خادم فعلي (مسودة معتمدة/سجل/أمر منفذ) —
  لا وعد بدون إثبات.
