# وثيقة استكمال وإطلاق وكيل SaaS

**الإصدار:** 2 — 18 أكتوبر 2026  
**الفرع الحالي:** `arena/a9de5c22-small-wakeel`  
**نوع الوثيقة:** خطة تنفيذ وقبول وتشغيل؛ ليست شهادة جاهزية أو موافقة نشر.

## 1. القرار التنفيذي

نواة SaaS موجودة ومربوطة بالتطبيق. المسموح حاليًا هو إعداد بيئة staging معزولة ببيانات اصطناعية، وليس فتح اشتراك تجاري عام أو الاعتماد على النظام وحده في الأموال الحقيقية.

**القرار الحالي: NO-GO للإطلاق العام المدفوع.** ينتقل إلى GO فقط بعد استيفاء بوابات القبول أدناه على نسخة إصدار محددة، وتسجيل أدلتها وموافقة أصحاب المسؤولية. لا يكفي أن تنجح الاختبارات على نسخة محلية مختلفة.

## 2. خط الأساس المثبت — وليس اختبارًا جديدًا

آخر بوابة مسجلة في التقرير المؤرخ 18 أكتوبر:

- **391 اختبارًا ناجحًا** عبر 45 ملفًا، 1731 assertion من Bun، وصفر فشل.
- **10/10** تقييمات توجيه عربي offline.
- build/typecheck ناجحان؛ صفر أخطاء lint مع 48 تحذيرًا، وتحذيرا tracing أثناء البناء.
- **49 طلب HTTP لمسارات SaaS** و**38 طلبًا ماليًا** على نسخة production مستقلة وقاعدة مؤقتة.
- 24 حالة SSR للشاشات واختبارات SaaS إضافية، وفحص Chromium منفصل فعلي لرحلات SaaS/المال/RTL/قطع SSE والتنقل المكتبي.
- ترحيل وsnapshot/quarantine/rotation وmail heartbeat بخمس أدوات maintenance نجحت اصطناعيًا، وSIGKILL مالي فعلي نجح؛ ليست إثبات Docker أو استعادة إنتاجية.
- قاعدة `db/custom.db` الأصلية لم تُعدّل. العمل محلي، ولم يثبت نشره أو تشغيل CI مستضاف على release SHA جديد.

**شُغّلت البوابة الكاملة بعد التنفيذ؛ هذه النسخة توثّق نتيجتها، ولا تُعد بديلًا عن قبول SHA الإصدار على البيئة المستهدفة.** سجل `/tmp` المذكور في التقرير مؤقت؛ يجب حفظ دليل الإصدار في نظام artifacts دائم ومقيّد الوصول عند اعتماده.

## 3. حدود المنتج التي يجب إعلانها بوضوح

### موجود الآن

حسابات أصلية، جلسات قابلة للإبطال، تحقق بريد/استعادة/MFA، عزل منشآت، فرق ودعوات وأدوار، تجربة وحدود طلبات persistent، إدارة استحقاق يدوي للمشغّل، طابور بريد مشفّر وعامل تشغيل، وترحيل وتدوير أسرار offline.

### ليس موجودًا أو ليس مُعتمدًا

- دفع إلكتروني أو فاتورة أو تجديد/استرداد آلي. الاستحقاق اليدوي **ليس دليل تحصيل**.
- بريد خارجي مثبت الوصول؛ الاختبارات تستخدم stub أو outbox اصطناعيًا مشفّرًا.
- مصالحة تلقائية لعمليات `EXECUTING` التاريخية؛ المسار الجديد أصبح claim/أثر/audit في transaction واحدة مع إثبات SIGKILL محلي، لا إعادة تصنيف للتاريخ.
- قبول حاوية/قرص/شبكة إنتاجية أو HA/serverless؛ قبول Chromium الاصطناعي المحلي موجود الآن، وليس قبولًا للبيئة المستهدفة.
- connector فعلي مثبت لـ POS/Excel؛ اكتشاف CLI-Anything ليس تكاملًا.
- حذف حساب self-service وسياسة خصوصية/احتفاظ معتمدة قانونيًا.

### قيود يجب ألا تتغير بصياغة تسويقية

1. التجربة الافتراضية: 14 يومًا، 5 مقاعد تشمل الدعوات المحجوزة، و50 **محاولة HTTP للمحادثة** لكل منشأة/يوم UTC؛ retries/replays تُحتسب. ليست محاسبة tokens أو قيمة مالية.
2. `active` في العقد اليدوي يستمر حتى إيقافه صراحة؛ `trialEndsAt` لا يوقفه تلقائيًا.
3. `/api/export` يتضمن كتالوجًا وعمليات/نقدية/audit، لكنه ليس full account/DB backup؛ `/api/restore` يستعيد الكتالوج فقط. دفتر كامل يُستعاد من SQLite snapshot مع المفاتيح والمصالحة.
4. `WAKIL_STRICT_APPROVALS=1` يعني اعتمادًا إداريًا، **وليس four-eyes**؛ يمكن للمدير اعتماد مسودته.
5. مالك المنشأة ليس مدير النشر. بيانات providers العامة وعمليات التشغيل العامة ليست صلاحيات عميل SaaS.
6. انتهاء الاشتراك لا يلغي المصادقة أو يمنح شخصًا صلاحية قراءة لم تكن له؛ RBAC يظل مطبقًا.

## 4. سجل بوابات الإطلاق

المسؤوليات التالية **أدوار مطلوبة للتعيين**، وليست أشخاصًا عُينوا أو مهامًا أُغلقت.

| البوابة | الأولوية | الحالة الحالية | المسؤول المطلوب | دليل الإغلاق |
|---|---|---|---|---|
| G1 — التعافي المالي بعد التوقف | P0 | التنفيذ المحلي وإثبات SIGKILL مكتملان؛ قبول التخزين/المراجع مفتوح | Backend + مراجع مالي/تشغيلي | تصميم معتمد، تنفيذ، اختبارات قتل عملية، وعدم تكرار أثر/فقد audit. |
| G2 — عزل وصلاحيات ومتصفح | P0 | backend + Chromium مثبتان محليًا؛ المصفوفة الكاملة/الإتاحة مفتوحتان | Backend/Security + QA | مصفوفة مسارات/أدوات وأدوار، browser E2E وتقارير منع التجاوز. |
| G3 — بريد حقيقي وحماية التسجيل | P0 قبل فتح التسجيل | الكود موجود؛ التجهيز والقبول مفتوحان | Operations + مسؤول النطاق | وصول حقيقي، idempotency، فشل وإعادة محاولة، مراقبة وبوابة abuse. |
| G4 — قاعدة ونسخ/استعادة ومفاتيح | P0 قبل بيانات العملاء | snapshot/rotation/quarantine مثبتة اصطناعيًا؛ قبول الهدف مفتوح | Operations + صاحب البيانات | استعادة على قرص مستهدف، فك MFA/outbox، RPO/RTO مقاسان. |
| G5 — تحصيل واشتراك تجاري | P0 قبل بيع اشتراك إلكتروني | غير منفذ؛ يدوي فقط | Backend + مسؤول تجاري/مالي | sandbox موثّق، webhook/reconciliation، فواتير/إلغاء/استرداد حسب السياسة. |
| G6 — مراقبة وحوادث وسعة | P0 قبل الاستخدام الحقيقي | health/heartbeat/alerts منفذة؛ paging/حوادث/سعة مفتوحة | Operations + الدعم | لوحات وإنذارات وتجارب حوادث واختبار سعة موثق. |
| G7 — خصوصية وشروط ودعم | P0 قبل الإطلاق العام | غير معتمدة | صاحب المنتج + مختص قانوني | سياسات معلنة وإجراءات وصول/حذف/احتفاظ ودعم معتمدة. |

| G9 — connector خارجي | حسب ما يُباع | غير مثبت | مسؤول التكامل | sandbox/read-back وصلاحيات وحدود وإعادة تشغيل؛ وإلا يُستبعد من العرض. |

لا تُغلق بوابة بسبب وجود ملف كود أو نجاح SSR فقط. يمكن استبعاد G9 من نطاق الإطلاق بشرط عدم عرض الميزة كمتصلة. ويمكن اختيار نموذج بيع يدوي بدل الدفع الإلكتروني فقط بقرار تجاري معلن وسياسة تسوية وإيقاف واضحة؛ لا يُغلق بذلك G1–G4 وG6–G8.

## 5. ترتيب التنفيذ المقترح

### المرحلة A — تثبيت النسخة وحدود الأمان

1. تحديد المرشح للإصدار وحفظ artifact ورقم SHA؛ منع إدخال أسرار أو قواعد عملاء في Git/artifacts العامة.
2. تشغيل البوابة الكاملة على نفس النسخة في CI المستضاف، وتوثيق التحذيرات والاستثناءات بدل إخفائها.
3. تنفيذ G1، ثم إعادة اختبارات المال والعزل والجلسات على التغيير الناتج.
4. توسيع مصفوفة الصلاحيات إلى المسارات والأدوات والمهام الداخلية، لا إلى HTTP وحده.

### المرحلة B — قبول البيئة والرحلات

يمكن تجهيز نطاق البريد وبيئة staging والمتصفح والنسخ بالتوازي، لكن ببيانات اصطناعية وتسجيل عام مغلق. إثبات استعادة القرص والمفاتيح والتعامل مع أعطال البريد يسبق بيانات العملاء.

### المرحلة C — الاشتراك التجاري

اعتماد سياسة البيع أولًا، ثم مزوّد الدفع إن كان ضمن النطاق. تنفيذ settlement قبل السماح بتغيير الاستحقاق تلقائيًا. لا يوصل webhook خارجي مباشرة إلى endpoint الإدارة الحالي ولا تُمنح له صلاحية مدير النشر.

### المرحلة D — قبول إصدار ونشر محدود

مراجعة الأدلة، ثم staging كامل، ثم مجموعة محدودة يوافق عليها صاحب المنتج بعد إغلاق بواباتها، ثم مراجعة قرار الفتح العام. **هذه مراحل تابعة للأدلة، وليست وعدًا بمواعيد.** أي تقدير زمني يبدأ بعد تعيين المسؤولين والبيئة والمزوّدين، ويُسجل منفصلًا كتقدير لا كحقيقة.

## 6. حزمة العمل G1 — التعافي المالي

### القرار الهندسي المنفذ محليًا

دمج claim والأثر والتحقق والحالة النهائية وaudit في transaction SQLite واحدة في `executeOperation`. لم تعد EXECUTING حالة وسطية دائمة في المسار الجديد. savepoint يعيد الأثر قبل FAILED_SAFE؛ إذا تعذر rollback أو كتابة terminal/audit، تفشل transaction كلها بما فيها claim. عند ضياع إقرار commit تُقرأ النتيجة النهائية المطابقة لما أعده هذا التنفيذ فقط. الصلاحية/العضوية/الخطة والـ tenant تُفحص داخل transaction؛ لا يُحوَّل conflict عادي إلى نجاح.

### دليل القبول المحلي المنفذ

- 25 اختبارًا ماليًا/162 assertion، بما فيها التنافس والعكس وفشل audit مرتين وعدم تعديل EXECUTING تاريخي.
- `bun run smoke:crash`: SIGKILL حقيقي في خمس نقاط بعد claim/stock/cash وقبل commit وبعده، ثم reopen لنفس الملف والتحقق من المخزون والدين والنقدية وaudit وintegrity/FK. فقد acknowledgement يُحاكى منفصلًا.
- قبل commit لا أثر وpending؛ بعد commit/retry أثر واحد وسجل نجاح واحد، وإعادة اعتماد مكتمل 409.
- Chromium يلغي SSE بعد start، ينتظر حفظ الرد ثم يعيد turn نفسه: replay دون مسودة أو أثر مالي ثانٍ. الاستمرار محدود بعملية حية، وليس durable chat عبر موت السيرفر.

### ما لا يغلقه هذا الدليل

حالة EXECUTING من كود قديم لا يجوز reset/reapprove عميانيًا؛ لا أثر رجعي للضمان الجديد. فشل كتابة/audit مُختبر fault-injection، لكن امتلاء قرص فعلي/power loss وقرص الاستضافة وRPO/RTO والمصالحة التشغيلية تحتاج بروفة مستقلة. لا يُختلق فشل آمن عند تعذر تحديد النتيجة.

قبول G1 النهائي يحتاج مراجعة المشغّل/المراجع المالي على artifact وقرص الهدف مع حفظ الأدلة، لا مجرد status نصي أو نجاح محلي.

## 7. حزمة العمل G2 — الهوية والمتصفح والصلاحيات

**التقدم:** رحلات Chromium الأساسية أدناه، قطع SSE، مصروف واعتماد، التنقل المكتبي و390px RTL نُفذت محليًا ضمن `bun run ci`. لا يثبت ذلك كل السيناريوهات أو كل الأجهزة/قارئ الشاشة؛ تبقى المصفوفة الكاملة والقبول المستقل.

| السيناريو | النتيجة المطلوبة |
|---|---|
| تسجيل مالك ثم التأكيد | مساحة فارغة، لا كتابة قبل التأكيد، ثم كتابة مسموحة بالدور. |
| رابط فتحه scanner أو GET | لا يُستهلك؛ لا action حتى POST الصريح. |
| رابط منتهي/مستخدم أو بريد دعوة مختلف | رفض واضح دون عضوية أو tenant جزئي. |
| قبول دعوة لمستخدم جديد/حالي | عضوية صحيحة فقط، دوران الجلسة، وعدم إنشاء منشأة إضافية للمستخدم المدعو الجديد. |
| تغيير IDs/headers أو resource ID لمنشأة أخرى | منع قراءة/تعديل بلا تسريب بيانات الطرف الآخر؛ اختبار البحث/التصدير/المحادثات أيضًا. |
| إيقاف عضو أو خفض دوره | الجلسات المتأثرة لا تنفذ طلبًا جديدًا بالصلاحية القديمة؛ يوثق سلوك الطلبات الجارية. |
| reset وMFA | تبطل الجلسات المطلوبة، MFA لا يختفي، recovery code لا يعمل مرتين. |
| تبديل منشأة أو حساب في تبويب/تبويبين | لا بيانات cache أو actor headers من السياق السابق، وتعافٍ مفهوم من CSRF قديم. |
| انقضاء التجربة أو بلوغ quota | رسائل صحيحة، لا التفاف عبر الأدوات/المهام، والقراءة/التصدير بحسب الدور. |
| هاتف وRTL وإتاحة | لوحة مفاتيح، قارئ شاشة، focus/errors، تكبير، reduced motion وشبكة بطيئة. |

تسجل المصفوفة كل endpoint/tool: الفعل، الدور، نوع المورد، قواعد tenant/ownership، إعادة التحقق داخل المجال، واختبار إيجابي وسلبي. تضم الأدوار غير المعروفة والحساب/العضوية المعطلة وoperator credentials. اختبار API لا يثبت صحة الواجهة؛ ونجاح الواجهة لا يثبت صلاحية backend.

## 8. حزمة العمل G3 — البريد

### عقد الخدمة

العامل الحالي يرسل `{to,subject,text}` إلى HTTPS public gateway مع Bearer وidempotency key ثابت. يعود gateway بـ 2xx بعد قبول الرسالة **بشكل دائم**، ويضمن منع التكرار على المفتاح. النقل at-least-once؛ ليس exactly-once ولا دليل وصول نهائي إلى صندوق البريد.

### قبول عملي على نطاق staging

1. إعداد sender وSPF/DKIM/DMARC وسجلات bounce/complaint وقيود الإرسال.
2. استلام فعلي لتأكيد حساب وreset ودعوة على صناديق اختبار يملكها الفريق.
3. التحقق أن الرابط canonical HTTPS وأن token في fragment، ولا يظهر في access log أو analytics/screenshots العامة.
4. محاكاة timeout/رفض gateway/قبول مع ضياع الرد وإعادة تشغيل العامل؛ لا رسائل مكررة عند إعادة المفتاح نفسه.
5. اختبار retry/backoff والخمس محاولات وstale lease وتنظيف payload المنتهي؛ لا إعادة بث عمياء لطابور قديم.
6. مراقبة queue age/failed/restarts ووجود operator مسؤول عن المشكلة.

لا تستخدم endpoint اختباريًا أو قراءة رمز من DB لإعلان نجاح البريد الحقيقي. لا تُنشر محتويات الرسائل أو MFA أو الرموز أو عناوين العملاء في artifacts عامة.

## 9. حزمة العمل G5 — الدفع والاستحقاق

**هذا القسم تصميم مطلوب، وليس وصفًا لتكامل موجود.** قبل كتابة connector، يُحسم البلد/العملة/الكيان التجاري والضرائب وسياسة التجديد والإلغاء وفترة السماح والفواتير واسترداد المال.

### متطلبات لا يجوز تجاوزها

- checkout يبدأ من backend؛ السعر والعملة والخطة لا تؤخذ من قيمة يعلنها المتصفح.
- webhook مستقل: تحقق signature على raw body، حدود الحجم/الزمن ونافذة replay وفق عقد المزوّد، ومفاتيح منفصلة عن مفاتيح المستخدم ومدير النشر.
- ربط provider customer/subscription بالمنشأة ربطًا خادميًا؛ لا tenant ID غير موثق من payload العميل.
- سجل event ID فريد ومعالجة ذرية؛ duplicated/out-of-order events لا تعطي مقاعد أو مدة إضافية.
- فصل سجل الفوترة التجاري عن نقدية ومبيعات متجر العميل؛ لا خلط بين تحصيل اشتراك وكيل ودفتر منشأته.
- التعامل مع pending/failed/canceled/refunded/disputed، وتسوية دورية مع مصدر المزوّد؛ redirect المتصفح ليس إثبات دفع.
- حدود المقاعد الحالية والدعوات عند downgrade؛ سياسة معلنة للقراءة والتصدير عند التعليق.
- audit منقّح ومراقبة للفروقات، مع آلية تصحيح معتمدة دون تعديل عشوائي في DB.

القبول يتضمن دفع sandbox ناجحًا وفاشلًا، webhook معادًا/مزورًا/متأخرًا، انقطاعًا بعد commit، إلغاءً واستردادًا وتغيير خطة، وتسوية تجد خطأ مزروعًا وتصلحه وفق السياسة. لا تُخزن بيانات بطاقة أو CVV داخل التطبيق.

## 10. النشر — مسودة إجراء تحتاج بروفة

هذه الأوامر **قوالب تشغيل للمشغّل وليست أوامر جرى تنفيذها هنا**. Docker/Compose غير مثبت التشغيل في أدلة هذه المرحلة. يُستخدم ملف البيئة الخاص بالمشغّل عبر secret injection، لا يُنسخ إلى Git، ولا تُنشر مخرجات `docker compose config` التي قد تكشف أسرارًا.

### قبل لمس قرص مستهدف

- اختيار نسخة artifact ثابتة؛ تأكيد Node/Bun والأوامر المطلوبة على الهدف.
- توفير canonical HTTPS origin وTLS وreverse proxy يستبدل forwarding headers الواردة من العميل.
- قرص SQLite دائم ونسخ off-host ومفتاح خارجي محفوظ بإصدار معلوم، وصلاحيات وصول محدودة.
- إبقاء `WAKIL_SIGNUP_ENABLED=0` و`WAKIL_SCHEDULER=off` حتى القبول الخاص بكل منهما.
- توفير credential إداري مستقل للـ health probe؛ حساب مالك SaaS لا يكفي.
- قاعدة موجودة بالـ base schema؛ migration الجديد **ليس تهيئة قاعدة فارغة كاملة**. لا seed على بيانات العملاء.

### ترتيب Compose المقترح بعد تجهيز الأسرار والقرص

```bash
# افحص التكوين دون طباعته، ثم ابنِ artifact المرشح.
docker compose config --quiet
docker compose build wakil

# نافذة صيانة: امنع المرور واوقف كل كاتب، بما فيه أي cron خارج Compose.
docker compose --profile mail stop

# خذ snapshot كاملًا متسقًا بأداة تشغيل موثوقة واحفظه خارج المضيف.
# اختبر نسخة استعادة، ثم طبق الترحيل على القرص المقصود فقط.
docker compose run --rm --no-deps wakil bun maintenance/migrate.js

# ابدأ الويب مع بقاء التسجيل العام مغلقًا.
docker compose up -d wakil
# بعد إعداد وقبول gateway فعليًا، شغّل عامل البريد الاختياري.
docker compose --profile mail up -d mail-worker
```

تستخدم الخدمات volume نفسه. الاسم المحلي للصورة في Compose ليس تعريف إصدار immutable؛ سجّل image digest/وسم الإصدار الثابت في سجل النشر واضبط عملية الترويج وفقه قبل الإنتاج. لا تفترض أن استبدال الصورة ينشئ/يرحّل volume قديمًا تلقائيًا.

أداة snapshot متاحة من checkout موثوق أو `maintenance/db-snapshot.js` المبني داخل الصورة؛ يجب أن يستطيع التشغيل الوصول إلى المسار المركّب:

```bash
# مسارات مثال تُستبدل بمسارات القرص والنسخ الفعلية؛ الوجهة جديدة لا موجودة.
DATABASE_URL=file:/absolute/mounted/wakil.db \
  bun run db:snapshot --output /secure-backups/wakil-before-release.db
```

الأداة ضمن خمس maintenance entrypoints الآن؛ في runner استخدم `bun maintenance/db-snapshot.js --output /private-backups/new.db` مع DATABASE_URL مطلق ومجلد مركّب خاص. تنشئ مجلدًا 0700 وملفًا 0600 وترفض الوجهة الموجودة. النسخة plaintext لبيانات العملاء وتحتاج تشفير التخزين خارج المضيف؛ حقول الأسرار المشفرة لا تشفر ملف DB كله. نسخ main-file حي ليس بديلًا آمنًا مع WAL. لم يُشغّل Docker هنا.

### التحقق بعد الإقلاع

- health بمفتاح المشغّل؛ المرفوض بلا هوية، والمقبول بالهوية الصحيحة، وإعدادات no-store/TLS/cookies.
- حساب اصطناعي: login/verify/invite/MFA/reset/expiry/CSRF ومحاولة tenant أخرى.
- حركة مالية اصطناعية مع read-back بعد إغلاق G1، دون إدخالها في دفتر عميل حقيقي.
- عامل البريد يعمل على DB والمفتاح نفسيهما؛ الرسالة تصل ولا يُكتفى بـ `processed` أو `sent` محليًا.
- اختبار restart وsnapshot restore والمراقبة ثم تسجيل نتيجة القبول. فتح التسجيل خطوة منفصلة بعد الموافقة؛ تشغيل scheduler خطوة منفصلة أيضًا.

## 11. التراجع والتعافي

### تراجع التطبيق فقط

مسموح إذا كانت النسخة القديمة **متوافقة** مع schema والبيانات الحالية. أوقف المرور/الكتّاب، اختبر artifact القديم على نسخة من DB الحالي، ثم قرر الرجوع. الترحيل الإضافي ليس ضمانًا أن نسخة قديمة تحترم membership/plan policies الجديدة؛ تعطيل SaaS أو تشغيل demo ليس rollback آمنًا.

### استعادة قاعدة من snapshot

ليست rollback بلا تكلفة: قد تفقد كتابات ملتزمة منذ وقت النسخة. يقرر صاحب البيانات/المسؤول المالي نطاق الفقد أو التسوية قبل أي تحويل مرور. احفظ DB المتعطل للتحقيق، واستعد إلى **مسار جديد**، مع المفتاح الموافق لها، ثم افحص integrity/foreign keys/schema والبيانات والأسرار. لا تكتب فوق النسخة الوحيدة ولا تمزج ملفات DB/WAL من أزمنة مختلفة.

قبل أي مرور بعد استعادة، ومع **كل الكتّاب متوقفين**، نفّذ احتواءً على المسار المستعاد، لا المصدر:

```bash
DATABASE_URL=file:/absolute/restored/wakil.db bun run recovery:quarantine
DATABASE_URL=file:/absolute/restored/wakil.db bun run recovery:quarantine --apply
# Runner: bun maintenance/restore-quarantine.js [--apply]
```

الافتراضي dry-run. Apply يعطل كل native accounts ويبطل sessions/links ويمحو mail payload/pending MFA والheartbeat، ولا يمحو active MFA أو دفتر المال. لا إعادة تفعيل تلقائي: قارِن تغييرات الهوية/كلمات المرور/MFA/الأدوار والإلغاء والاستحقاقات والأثر المالي منذ snapshot مع أدلة موثوقة. راجع pilot/operator credentials الخارجية منفصلًا؛ هذا الأمر لا يبطلها. لا تفتح الحسابات لمجرد أن integrity نجح. الأدوات المحلية/المعبأة مثبتة اصطناعيًا فقط.

### تراجع بعد تدوير مفتاح

كل snapshot يحتاج إصدار المفتاح الذي يطابق envelopes داخله. تغيير env إلى المفتاح القديم مع DB أُعيد تشفيره بالمفتاح الجديد يكسر providers وMFA والبريد. حافظ على ربط backup/key version، ولا تستأنف الويب أو العامل بمفتاحين مختلفين.

### RPO/RTO

يُعتمد الرقمان من صاحب البيانات بعد قياس drill على البيئة الفعلية. يمكن مناقشة هدف مبدئي مثل RPO ≤ 15 دقيقة وRTO ≤ 60 دقيقة، **لكنه اقتراح غير معتمد وغير مُحقق**. قياس 96ms في أحدث فحص اصطناعي ليس RTO تجاريًا.

## 12. المراقبة والاستجابة للحوادث

نُفذت إشارات operator health: عمر البريد >300 ثانية، عامل مفقود/آخر إكمال أقدم من300 ثانية عند توقع تشغيله، failed worker/mail، وأي EXECUTING. `WorkerHeartbeat` مقيّد بـ runId لمنع إكمال قديم. يُرجع health حالة degraded مع JSON alerts، لا يرسل تنبيهًا خارجيًا ولا يختبر وصول البريد (`externalDelivery:not_probed`). بقية thresholds أدناه مقترحات تشغيلية تحتاج baseline وpager على الهدف:

| الإشارة | trigger أولي مقترح | التصرف الأول |
|---|---|---|
| `EXECUTING` دون تقدم | أي حالة غير مفسرة أو تجاوز حد التنفيذ المعتمد | وقف الاعتمادات المتأثرة، حفظ الأدلة، لا reset/reapprove أعمى. |
| طابور بريد | oldest pending أكبر من 5 دقائق أو failed متزايد | فحص العامل/gateway/الوقت/المفتاح؛ إغلاق التسجيل عند تعذر وصول الأمان. |
| DB/قرص | integrity/foreign-key failure، قفل متكرر أو فشل كتابة | وقف الكتابة وحماية النسخ؛ لا اعتبار health 200 ضمانًا لسلامة المال. |
| auth | قفزة 401/429 أو MFA failures عن baseline | مراجعة abuse والـ proxy والثروتل؛ لا تعطيل CSRF/MFA لتجاوز المشكلة. |
| نسخة احتياطية | تأخر عن RPO المعتمد أو فشل استعادة/مفتاح | incident تشغيلي، علاج النسخة/المفتاح ووقف التوسع حسب قرار المخاطر. |
| دفع — بعد تنفيذه | signature failure/تأخر أو اختلاف settlement | رفض الحدث غير الموثوق، عزل المعالجة وتصحيحها وفق السجل. |

استعلامات قراءة للمشغّل المصرّح له فقط، باستخدام عميل SQLite موثوق يدعم read-only؛ لا تُرسل DB إلى موقع فحص عام:

```sql
SELECT status, COUNT(*) AS total, MIN(createdAt) AS oldest, MAX(attempts) AS attempts
FROM MailOutbox GROUP BY status;

SELECT status, COUNT(*) AS total FROM Operation GROUP BY status;
PRAGMA integrity_check;
PRAGMA foreign_key_check;
```

هذه aggregates لا تقيس التسليم النهائي ولا تحسم أثر عملية بعينها. التحقيق التفصيلي يحتاج وصولًا محدودًا وسجلًا آمنًا، لا نسخ payload أو الأسرار إلى issue أو chat.

### بطاقات تعامل سريعة

- **حساب عميل مخترق:** إبطال جلساته/تأمين الاستعادة وفق التحقق من الهوية، حفظ audit وفحص تغيير العضويات. operator/API credentials منفصلة ويجب إلغاؤها من إعداداتها إذا تأثرت؛ logout لا يلغي مفتاح مزوّد خارجي.
- **بريد متوقف:** إبقاء/إعادة التسجيل العام إلى مغلق، إصلاح gateway والعامل، إصدار روابط جديدة عند انتهاء القديمة؛ لا إرجاع payload قديم scrubbed.
- **مفتاح تشفير مفقود:** لا وعد بإعادة بناء MFA أو رسائل مشفرة من DB وحده. استخدم النسخة الصحيحة من secret backup وإجراء recovery معتمدًا؛ لا تُلغِ MFA جماعيًا بلا تحقق.
- **اشتراك يدوي انتهى:** إيقاف صريح من مشغّل مخوّل مع reason/audit وفق العقد؛ `trialEndsAt` وحده لا يكفي لحالة `active`.
- **حالة مالية مجهولة:** الحفاظ على DB والعمليات والوقت والنسخة، عزل الكتابات، ثم تسوية مخوّلة. فشل الاتصال ليس دليل فشل المعاملة.

## 13. الخصوصية والدعم والاحتفاظ

قبل جمع بيانات عملاء حقيقية يجب اعتماد:

1. جرد أنواع البيانات وأماكنها: DB، نسخ احتياطية، بريد، مزوّد موديل، telemetry، logs والدعم.
2. سياسة وصول أقل صلاحية للمشغّلين، مراجعة وصول، وتسجيل تدخلات الإدارة والاستحقاق.
3. مدد احتفاظ مستقلة للمالية/audit/الحسابات/البريد/logs والنسخ، مع آلية حذف/تقييد وقيود الالتزامات المالية والقانونية.
4. تصدير بيانات مطلوب للعميل وإثبات هوية طالب الوصول/الحذف. JSON التصدير الحالي لا يشمل كل بيانات الحساب/الخصوصية، ولا يفي وحده بهذا النطاق.
5. سياسة إنهاء العلاقة وملكية المنشأة عند مغادرة المالك؛ نقل الملكية/حذف الحساب ليسا ميزة مُنفذة هنا ويحتاجان تصميمًا واختبارًا.
6. شروط وتسعير وحدود ووقت استجابة دعم وإبلاغ حادث، وروابط واضحة قبل التسجيل المدفوع.

تنظيف worker الحالي محدود ومشروط بتشغيله كما يوضح دليل SaaS. ليس سياسة محو قانونية شاملة، ولا تُثبت هذه الوثيقة الامتثال لأي تشريع.

## 14. سجل قبول الإصدار — قالب يُملأ بالأدلة

| الحقل | القيمة المطلوبة قبل الموافقة |
|---|---|
| Release SHA + artifact digest | غير مسجل بعد؛ يجب أن يطابق النسخة المختبرة والمنشورة. |
| CI URL + artifact دائم | غير مثبت على الإصدار بعد. |
| schema/migration + key versions | أسماء الإصدارات فقط، **لا مفاتيح أو credentials**. |
| بيئة staging/هدف النشر | إعداد وموقع قرص وعامل وطريقة إشراف معتمدة. |
| G1–G9 | نتيجة كل بوابة، رابط الدليل، المسؤول/المراجع والتاريخ. |
| mail/browser/recovery/billing | أدلة فعلية؛ اكتب «خارج النطاق» فقط إذا استُبعدت الميزة بوضوح من المنتج. |
| RPO/RTO + آخر restore | أهداف معتمدة ونتيجة مقاسة وفروقات/تسوية معروفة. |
| مخاطر وتحذيرات متبقية | سبب القبول ومن وافق، دون إسقاط مانع مالي/أمني بتعليق مبهم. |
| خطة rollback/on-call | artifact متوافق، snapshot، key version، مسؤول اتصال وحدود الإيقاف. |
| القرار | NO-GO افتراضيًا حتى استكمال ومراجعة الأدلة. |

## 15. قائمة التسليم النهائية

- [ ] تطابق الكود المنشور والاختبارات والـ schema ونسخ مفاتيح الأسرار مع سجل إصدار واحد.
- [ ] إغلاق G1 وإثبات عدم تكرار أثر المال بعد الانقطاع/إعادة المحاولة.
- [ ] اجتياز مصفوفة الأدوار وtenant isolation ورحلات المتصفح والأمان.
- [ ] وصول بريد حقيقي وتشغيل العامل ومراقبته، مع بقاء أسرار ورسائل الاختبار خارج logs العامة.
- [ ] اجتياز استعادة القرص والأسرار على البيئة الفعلية وتوثيق RPO/RTO.
- [ ] تحديد نموذج البيع؛ قبول الدفع والتسوية إن كانا ضمن النطاق، وإلا إعلان الإدارة اليدوية وحدودها.
- [ ] اعتماد الخصوصية والدعم والاحتفاظ وشروط الاستخدام.
- [ ] إنذارات وإشراف وخطة حادث وتراجع ومسؤولون محددون.
- [ ] CI مستضاف ودليل SHA ومراجعة إصدار وموافقة صريحة قبل فتح التسجيل/الاستخدام العام.

**الخلاصة التنفيذية:** المستهدف التالي ليس زيادة عدد الشاشات أو تغيير NO-GO إلى GO في الوثيقة؛ بل إغلاق أصغر مجموعة من فجوات المال والهوية والتشغيل بدليل قابل للتكرار، ثم فتح المنتج على النسخة نفسها وبالحدود نفسها التي ثبتت.
