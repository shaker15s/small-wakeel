# وكيل: شغل فعلي، تخصيص الحساب، ومعرفة النشاط — نتائج التنفيذ

**18 أكتوبر 2026 — النتيجة: تنفيذ التطبيق واختبارات الحسابات/الواجهة ناجحة؛ قبول الموديل الحي محجوب وغير مثبت.**

## ما اتغير فعليًا

### 1) بداية بلا بيانات مصطنعة

- الأونبوردينج الجديد خطوة واضحة: هوية المنشأة/المستخدم الفعليين، حتى4 أولويات اختيارية، وضع سريع أو عميق، ولون إحصائيات من أربع لوحات معتمدة.
- الحفظ في `WorkspacePreference` بمفتاح منشأة + مستخدم، وليس علم localStorage عام. إكماله لا يُسجل على السيرفر قبل نجاح الحفظ؛ يوجد تأجيل صريح للوصول لإعدادات الحساب/تأكيد البريد، دون ادعاء أن الإعداد اكتمل.
- التسجيل وإنشاء مساحة SaaS يدعمان الأنشطة التسعة، بمنشأة فارغة. منشئ الأنشطة القديم أصبح atomic وبلا عملاء أو موردين أو موظفي وردية أو أصناف وأسعار وأرصدة تجريبية؛ رصيد البداية الافتراضي صفر. أسماء الأصناف التي يكتبها المستخدم تبدأ بصفر سعر/مخزون حتى استكمال البيانات.
- مسار تأسيس الأونبوردينج القديم `mode=provision` يرد410 بدل الكتابات المتتابعة الجزئية. مسار تحليل الصور/النص القديم لا يخترع أسعارًا أو كميات عند انقطاع الموديل: يرد503 وصفوف استخراج فارغة. أي تحليل حقيقي للمراجعة فقط، وليس استيرادًا أو ربطًا مثبتًا.
- أصل `db/custom.db` ترك كما هو، بما فيه بياناته التجريبية القديمة؛ لم نحذف بيانات مستخدم أو ننقلها لمستخدم SaaS جديد. الأنشطة القديمة ليست شهادة أن الأرقام تمثل متجرًا حقيقيًا.

### 2) اختصارات من الاستخدام الحقيقي

- اقتراحات المستخدم مستقلة داخل نفس المنشأة: تنبيهات من السجل، أكثر الأدوات استخدامًا خلال14 يومًا، أولوياته الصريحة، وذاكرته النشطة.
- اختفى demo النشاط والاقتراح الزمني غير المستند لاستخدام، وكذلك fallback أمثلة المحادثة عندما تتعطل خدمة الاقتراحات.
- الطلب المتكرر يظهر بعد3 استخدامات؛ الطلبات المالية تظهر كبداية مسودة تطلب التفاصيل، **لا تعيد اسمًا أو مبلغًا أو كمية قديمة**. الصلاحيات ترشح أنواع الكتابة المتاحة.
- تقرير قراءة متكرر5 مرات على3 أيام مختلفة بالقاهرة يمكن أن ينتج اقتراح جدولة لصاحب صلاحية automation.manage. قراءة الاقتراح لا تنشئ مهمة ولا تنقل فلوسًا.
- أداة الشات ترفض إنشاء مهمة من رسالة اقتراح فقط، أو بموعد/ساعة ناقصين، أو بأداة كتابة مالية. التفعيل يحتاج طلبًا صريحًا وموعدًا مستقبلًا واضحًا؛ التكرار daily/weekly/monthly محفوظ فعلًا.
- مواعيد الشات تحوّل ساعة القاهرة إلى UTC دون الاعتماد على timezone السيرفر، والتقارير الدورية تحافظ على ساعة القاهرة عبر انتقال التوقيت الصيفي. الشهر ينتهي عند آخر يوم متاح بدل تجاوز الشهر الأقصر.
- الاستخدام محدود بآخر2000 حدث خلال14 يومًا. هذا تخصيص إحصائي محدود وذاكرة/إعدادات، **وليس تدريب أوزان ذاتيًا ولا توصية معصومة**.

### 3) «غيّر لون الإحصائيات» من الشات

- أداة `configure_workspace` تحفظ accent/density/responseMode/goals للمستخدم الحالي في المنشأة الحالية فقط، مع سجل audit.
- `workspace.personalize` متاح للأدوار المعروفة الأربعة لتخصيص واجهتهم فقط. الأدوار المجهولة مرفوضة، وعضوية/تأكيد البريد/الاشتراك يعاد فحصها عند الكتابة. عبور الحسابات والمنشآت مرفوض من API ومن دالة الحفظ.
- ألوان amber/teal/indigo/rose، وكثافة comfortable/compact؛ لا CSS أو HTML أو JavaScript حر، ولا كود مشروع أو role أو رصيد افتتاحي ضمن هذا المسار.
- رسم المبيعات في الإحصائيات يستخدم اللون المحفوظ؛ كثافة الجداول تستخدم token محدودًا. بيانات المستخدم السابق لا تظل لون المستخدم التالي.
- نجاح الشات يعتمد على نتيجة الحفظ، وليس جملة يختلقها الموديل؛ تحديث الواجهة يأتي من إعادة تحميل تفضيلات الحساب بعد اكتمال الرد.
- هذه نسخة فعلية محدودة من واجهة قابلة للتخصيص، وليست إذنًا للموديل بتعديل أي ملف أو كل تفاصيل التصميم.

### 4) إضافات حقيقية داخل صندوق صلاحيات

- وصل الهارنيس أدوات install_plugin/list_plugins/run_plugin/toggle_plugin بالتنفيذ والتخزين الفعليين.
- التثبيت والتفعيل يحتاجان tools.manage؛ لم يعد middleware يثبت/يفعل إضافة تلقائيًا لأن المستخدم سأل عن تحليل. طلب إيقاف/تعديل إضافة لا يعامل كـtrigger لتشغيلها قبل التعديل.
- وحدات التنفيذ: inventory_audit، sales_analytics، margin_audit، receivables_aging، supplier_payables، expiry_shield. قراءة فعلية من قاعدة البيانات، بلا تنفيذ كود حر أو SQL حر أو دفع آلي.
- وحدة مجهولة أو custom_query التي كانت تُرجع جدول مخزون عام تحت أي اسم أصبحت مرفوضة. طلب خارج وحدات المترجم المحددة لا يتحول لتقرير عام يدعي أنه الميزة المطلوبة.
- تثبيت الإضافة واختصار صاحبها وaudit معاملة واحدة؛ الفشل لا يترك تثبيتًا نصف مكتمل. التوقف يمنع التشغيل، وتحديث registry لا يحتفظ بتفعيل قديم بعد الإيقاف/الحذف.
- المترجم الحتمي يجمع وحدات معروفة، وليس محاكاة لموديل حي. الواجهة تعرض مصدره «تجميع وحدات معتمدة — بدون استدلال حي» بدل تسميته توليد ذكاء اصطناعي.
- حدود مهمة: مخرجات وصف الإضافة من الموديل لا تضمن أن أي طلب خارج قدرات الوحدات قد نُفذ. راجع الوحدات والتقارير الفعلية؛ لا تكامل خارجي أو حجز أو رسائل بمجرد اسم إضافة.

### 5) سريع وتفكير أعمق

- زران ظاهران في مربع الكتابة، مع حالة اختيار، وحفظ الوضع الافتراضي لكل مستخدم/منشأة. عند تعذر الحفظ يظهر أنه تبديل للجلسة فقط.
- السريع يختار مسار flash، والعميق pro/deep حسب المزود المتاح؛ نفس صلاحيات وأمان الأموال في الحالتين. اسم المزود الذي رد بالفعل يبقى المرجع، والاختيار ليس ضمان توفر الموديل أو جودة إجابته.
- «بحث إنترنت» منفصل عن العمق. أزيل mock search كخيار افتراضي وكـfallback بعد فشل SDK. المزوّد غير المتاح يعطي نتيجة فشل/غياب خدمة بدل مصادر صناعية؛ HTTP search يستخدم نقلًا عامًا HTTPS مع حماية الشبكة.
- مزودو localhost/HTTP القديمون لا يعرضون كاختيارات موديل حي في bootstrap؛ تبقى إدارة التهيئة القديمة متاحة لمسؤول التشغيل دون حذف قاعدة البيانات.

### 6) برومبت بمعرفة تخصصية موثقة

التغطية: سوبر ماركت، جيم، صيدلية، عطارة، مطعم، عيادة، إلكترونيات، جملة، ملابس. يُحقن سير عمل النشاط وحدود قدرته ومصادره، مع سياسة الصلاحيات، وإعدادات المستخدم، والإضافات الفعلية المفعلة. النشاط المخصص يطلب سير العمل بدل استيراد أمثلة نشاط آخر.

## اختبار الموديل الحي — لم ينجح، ولا نحسب الـfallback نجاحًا

شُغّل `bun run model:acceptance` على نسخة مؤقتة migrated، **بلا mock.module أو استبدال fetch/SDK**. اختير الموديل الخارجي المحفوظ `agnes-3.0-flash`؛ النتيجة النهائية **blocked / exit2**. لم يصل رد حي صالح يثبت قراءة البرومبت. لا Gemini key أو إعداد SDK محلي متاحان؛ يوجد مزود خارجي محفوظ لكن تواصله لم يتأكد من هذه البيئة. لا نعرض المفاتيح أو أخطاء قد تتضمنها.

التقرير المحلي غير المتتبع: `.ci-results/live-model-acceptance.json`. الاستنتاج الصحيح: **التنفيذ المالي المحلي مثبت، أما جودة وفهم الموديل الفعلي وقبوله البرومبت فغير مثبتين حاليًا**.

عند توفير مزود صالح يمكن الوصول إليه من بيئة التشغيل، الاختبار نفسه جاهز لقياس:

1. علامة عشوائية داخل system فقط يعيدها الرد، وhash/طول system والأدوار بعد استجابة فعلية؛ تسع حالات تشغيلية بسيطة، واحدة لكل نشاط. اختبارات محدودة وليست benchmark شاملًا.
2. طلب أداة `record_expense` من رد الموديل نفسه، مرورًا بالهارنيس الحقيقي، وإنشاء مسودة17.35 جنيه بلا أثر قبل الاعتماد.
3. اعتماد فعلي وإعادة طلب داخل القاعدة المعزولة؛ أثر واحد1735 قرشًا. لا يسمح بنجاح parser/قواعد محلية بدل طلب أداة حقيقي من الموديل.

الوضع strict لا ينتقل إلى مزود/SDK احتياطي ولا يحتسب غياب الرد نجاحًا. السكربت يحتفظ بإجابات الموديل في الذاكرة للتحقق فقط، ولا يحفظ نص البرومبت أو الرد الخام في التقرير.

```bash
# لا تضع المفاتيح في الشات أو ملفات Git؛ استخدم إعداد التشغيل الآمن.
bun run model:acceptance
# يمكن اختيار معرّف موديل مهيأ فعلاً:
WAKIL_LIVE_MODEL_KEY='ext:<configured-model-id>' bun run model:acceptance
```

## التشغيل والترحيل

أضيف `db/migrations/20261018_workspace_preferences/migration.sql`. **لم يُطبق على قاعدة المصدر** حفاظًا عليها. عند تشغيل التحديث على قاعدة مستخدم حقيقية، خذ نسخة احتياطية ثم طبق الترحيلات من مسار التشغيل المعتاد قبل فتح الواجهة:

```bash
DATABASE_URL='file:/absolute/path/to/your.db' bun run db:migrate
```

لا seed تلقائي، ولا push أو نشر أو تحويل مال حقيقي تم في هذه المهمة.
