## 3) البوابة P1 — «الثقة» (لا رد غلط، لا شاشة فاضية، لا شبكة تحرق وقت)

**المعيار:** كل أمر في §5-G1 أخضر. لا بند يُغلق بدون اختبار دائم يثبت إصلاحه.

### 3.1 قاعدة الداتا الملتزمة (D4) — أول شيء
1. ترحيل `db/custom.db` الملتزمة إلى حالة الـ schema الحالية (مرحلات aditive فقط) + **إعادة توليد الديمو**: 4 أنشطة عرض حقيقية (سوبر ماركت النور، عطارة المسك، صيدلية الشفاء، جيم الأبطال) **بما فيها نشاط `cashbook`** (محل الكاشير الوحيد — الشخصية الرئيسية D6) ونشاط `inventory` كامل.
2. **Auto-migrate عند إقلاع dev** (idempotent، dev-only، بصوت صامت مع سطر واحد) — clone جديد = `bun install && bun dev` وشغال.
3. بوابة CI: `bun run db:sync --check` على **الملف الملتزم نفسه** (وليس على نسخة) — لا تلتزم قاعدة منحرفة أبدًا.
4. احتياط: snapshot للقاعدة الأصلية قبل اللمس (التزام الريبو الحالي محفوظ كمرجع).

### 3.2 الـ 9 فجوات في يوم الشغل (D2) — كل فجوة = إصلاح + اختبار دائم
| الفجوة | الإصلاح المستهدف | مكانه |
|---|---|---|
| «بعت ٣ كيلو جبنة رومي بـ٤٥٠ **للكيلو**» → بلا مسودة | قراءة سعر الوحدة × الكمية = إجمالي (السيناريو R32-3 تكرر في صيغة «رومي» المركبة) | `cashbook-parser` / `ruleBasedIntent` |
| «بعت كرتونة لبن جهينة **لأحمد ودفع ١٠٠ بس**» → بلا مسودة | «بس/فقط» بعد مبلغ = دفع جزئي، والباقي آجل | نفس الأعلى + `resolvePaid` |
| «حصلت ١٠٠ من أم حسن» → بلا مسودة | تحصيل من عميل موجود في السجل (مطابقة الاسم قبل «مفيش») | `ruleBasedIntent` |
| «اشتريت ١٠ كيلو رز من شركة الألبان بـ٢٥٠» → بلا مسودة | شراء من مورد بالاسم (مطابقة مورد) بدون صنف — نمط الدفتر اليدوي | `ruleBasedIntent` + `cashbook-parties` |
| «السلام عليكم» → رد غير مرحب | تحية = رد حتمي ودّي فور (مثل سؤال الهوية) | PASS 0a الجديد «تحية» |
| «بعت ٥٠ جرام عنبر بـ٣٤٠٠» (عطارة) → بلا مسودة | بيع بوحدة وزن + سعر إجمالي للعطار | vertical attar parser |
| «كيلو الكمون بكام؟» (عطارة) → بلا كارت | سؤال سعر صنف = `get_item_stock`/`search_catalog` | PASS 1 read-routing |
| «عمر الشناوي **عضويته** باقي قد إيه؟» → بحث باسم «الشناوي عضويته» | حارس كلمات السؤال الموسع (السيناريو R32-5 تكرر) — كلمة «عضويته» اسم possessive لا جزء من الاسم | `isQuestionWord` + harness |
| «بعت ٢ أوريو بـ٣٠» (كاشير) → بلا مسودة | مطابقة الصنف + صلاحية الكاشير للمسودة (لا «تم» كاذب ولا رفض صامت) | grounding |

**البوابة:** `bun run sweep` = **44/44** على `WAKIL_OFFLINE=1` (بلا موديل نهائيًا) + حالات جديدة تضاف للـ sweep لكل إصلاح.

### 3.3 رحلة «ضيف أحمد» (D3)
1. إصلاح `scripts/accept-ahmed.ts`: ترويسات `x-wakil-business`/`x-wakil-user` (عقد المتصفح الحقيقي).
2. توسيع عقد API: `POST /api/operations/[id]/confirm` يقبل `businessId` في **الجسم** أيضًا (لمستهلكي API خارجيين) — الاختبار يثبت المسارين.
3. إضافة إلى الرحلة: **التحقق بعد الاعتماد** أن الرصيد الجديد قابل للقراءة بالشات («أحمد عليه كام؟» → ٤٥٠) — موجودة، تُثبت في البوابة.
4. **البوابة:** `bun run accept` = **9/9**.

### 3.4 الشاشات (D5)
1. **JournalView**: إيجاد سبب «شبه فاضية» في SSR (مُشتبه: استعلام يفشل server-side في حالة أول يوم) + إصلاح + حالة فراغ عربية بـ CTA.
2. **حالات الفراغ** لكل الشاشات: نص عربي + زر إجراء (أول صنف؟ ابدأ بالشات) — عتبة المحتوى المقاسة في `screens-audit` ترفع لكل شاشة.
3. **البوابة:** `bun run screens` = **64/64**.

### 3.5 سرعة + شبكة (D1 جزئيًا)
1. **Fail-fast الموديل:** لو `zaiAvailable()` = false ولا `GEMINI_API_KEY` ولا مزوّد external **صحيحة الـ probe** (circuit مفتوح / آخر فشل < 60s) → **تخطي محاولة الموديل كليًا** في الـ brain والـ intent → الـ turn حتمي 100%. (اليوم: محاولة فاشلة 1–4s ثم fallback.)
2. ميزانية زمن مقاسة: **p50 حتمي < 600ms** على الـ 44 نية (يُقاس في الـ sweep ويُكتب في التقرير).
3. مؤشر «المسار» في الشات: خطوة تفكير توضح بصريًا: `رد فوري (من السجل)` مقابل `عقلي شغّال (اسم الموديل)` مقابل `الموديل مش متاح — عملتها من السجل` — **صدق كامل، لا ادعاء**.
4. أخطاء الشبكة للواجهة: رسالة عربية + «جرّب تاني» (موجودة في حالة error للـ screens) + إعادة محاولة idempotent للـ turn (R34 `turnId`) — **اختبار regression في CI**.

### 3.6 توثيق الأدوات (D10)
`package.json`: إضافة `sweep` و`accept` كسكربتات رسمية + إضافتهما لـ `scripts/ci.sh` **قبل** الـ build (بوابة إلزامية).

## 4) البوابة P2 — «الموظف الحقيقي» (سوبر باورز الوكيل)

**المعيار:** الوكيل يعمل **بلا موديل** لكل العمليات العالية التردد، و**بموديل** للتعقيد — ويظهر كموظف يفهم البزنس ويتذكر ويستبق.

### 4.1 اختيار الأدوات: من JSON نصي إلى Function Calling أصلي (D7)
1. **عقد أدوات موحّد**: تعريف واحد (JSON Schema لكل أداة) يولّد من نفس المصدر: وصف البرومبت + `tools` لنظام الموديل (Gemini `tools`/OpenAI `tools`) + السكالا الحتمي.
2. **مساران للـ brain:**
   - الموديلات الداعمة: **function calling أصلي** (استجابة structured) — اختيار دقيق + حجة مضبوطة.
   - غير الداعمة: بروتوكول النص الحالي (يبقى كـ fallback مُقوّى).
3. **بنك تقييم لاختيار الأدوات** (30+ حالة: نية → الأداة المتوقعة بالاسم) يُشغَّل في CI (بحدود اصطناعية) وعند أي تغيير في الأوصاف — «تغيير وصف أداة = إعادة تشغيل البنك».
4. **حارس التنفيذ:** أي tool_call خارج الصلاحيات/الكتالوج = رفض معلن + تعلّم (لا تنفيذ كاذب، لا `ok:true` مُصطنع).

### 4.2 إعادة توازن المسارات (السرعة الحقيقية)
- **الحتمي أولًا** للنيات عالية التردد (بيع/شراء/تحصيل/خزنة/رصيد/مخزون/تسوية): إن كان الـ intent غير ملتبس على سلّم القواعد القوي (3.2) → **لا موديل أصلًا** — p50 < 400ms، صفر شبكة.
- **الموديل** للمركب/الغامض/المفتوح («حلللي مبيعاتي وقارنلي بالشهر اللي فات واقتلح خطة»).
- هذا ينفّذ طلب المستخدم حرفيًا: «من غير ما نروح للموديل اللي هو العقل» للعمليات اليومية.

### 4.3 التطور مع الاستخدام — «الموظف بيكبر» (الطلب الأساسي)
1. **ملف المورد (Supplier Profile):** من سجل المشتريات — مين يجيب إيه، كل قد إيه، بسعر قد إيه، وبيتأخر قد إيه. كارت «ملف المورد» + يظهر في اقتراحات الشراء. يتغذى من كل عملية شراء ناجحة (بدون تدخل).
2. **توقع النقص والاستباق:** `forecast_stockout` موجود → توصيله بـ **قائمة إعادة الطلب** (ShopReminder) + **البريف الصباحي**: «البيض هيخلص خلال ٣ أيام — عايز أسجل شراء من [أقرب مورد]؟» + بعد تنفيذ الشراء: **تذكير «افتكرت تجيب بيض؟» عند أول طلب مقبل** (حلقة الـ reminder تُختبر offline).
3. **الذاكرة الوظيفية (مش «ذاكرة» ظاهرة):** سياسات حفظ تلقائي محدودة ومعلنه: وعود السداد، تصحيحات المستخدم (in-scope)، تفضيلات، حقائق الأطراف، أنماط الموردين. **لا يظهر للمستخدم «مهمة مجدولة» أو «ذاكرة» — يظهر فقط الناتج** (تذكير، اقتراح، رقم صحيح). MemoryView يبقى لأغراض الإدارة (شوف/عدّل/امسح).
4. **التعلم من التصحيح (Reflection عميق):** رفض مسودة بسبب X → حفظ درس (kind=lesson) → المسودات المشابهة بعدها تعرض التحذير نفسه قبل الاعتماد. **اختبار:** نفس الخطأ مرتين = فشل البوابة.

### 4.5 خططا ومهام متعددة مرئية

### 4.7 الموظف يكمل معلومات البزنس بنفسه (onboarding ذكي)

## 5) البوابة P3 — «التصميم والموشن» (Apple-grade، full-screen)

**المبدأ:** البنية المعمارية الحالية تبقى؛ الجلد والعظام الجمالية تتغير. كل شاشة full-viewport.

### 5.1 نظام تصميم واحد (Design Tokens)
- توكنز مركزية في `globals.css` (Tailwind 4 theme): ألوان (navy/amber/warm-paper + dark)، 4 مقياس زوايا، 3 مستويات ارتفاع، حبر/سحب، **زمن حركة** (120/240/400ms + easing Apple: `--ease-apple/spring/glide` موجودة تُعمم)، safe-area.
- **Accent لكل نشاط** (workspace-options موجود) — البطل لونه هو هوية النشاط.
- وضعان: فاتح/داكن، **RTL كامل** — فحص تباين AA.

### 5.2 Full-bleed لكل الشاشات (طلب صريح: «الشاشات تاخد الشاشة باكمله»)
- الـ 9 شاشات: `100dvh` على الموبايل (safe-area + bottom-nav زجاجي)، edge-to-edge على اللاب/التليفون، عمق القراءة بقيد عرض **لنص المقروء فقط** (المحتوى البياناتي يمتد).
- لا horizontal scroll أبدًا (قائمة فحص `scrollWidth == clientWidth` على 390/800/1280px — موجودة في R18 تُحافظ عليها).

### 5.3 نظام موشن (مكتبة واحدة، لا scatter)
`src/components/motion/` — variants موحدة:
- `enter` (fade+rise+settle)، `spring-in` (كروت/أزرار)، `press` (scale 0.97)، `tick-up` (أرقام تعدّ تصاعديًا عند ظهورها)، `queue` (رسائل تنتظر)، `morph-success` (كارت مسودة → ناجح: أخضر + check رسمي).
- **Micro-interactions** لكل عنصر: hover-reveal على الكروت، shimmer على الهياكل، ripple خفيف على الإرسال، avatar «يفكر/يفرح/ينبه» (حالات موجودة تُربط بكل مسار).
- **reduced-motion**: كل حركة لها بديل ثابت (guard موجود يُعمم).
- **الصفحة ↔ الصفحة**: slide خفيف RTL-aware + حفظ scroll لكل شاشة.

### 5.4 شاشة البطل: الشات (ريديزائن كامل)
- glass pill + hover-intent + composer spring (أساس R18) → **صقل**: مؤشر كتابة أثناء streaming، thinking-timeline بخطوات مقاسة (ms لكل خطوة) + أيقونات، كروت البيانات بأنيميشن `tick-up` للأرقام، approval UX (مؤشر اعتماد ذري + morph)، طابور الرسائل المرئي، صوت (sfx موجود) مع كتم.
- **الصدق البصري:** كل كارت رقمي يحمل شارة «من السجل» + وقت التحقق.

### 5.5 لوحة اليوم (ريديزائن كامل — «مركز القيادة»)
- أول 500ms تعرض: **الخزنة (رقم كبير tick-up) · مبيعات اليوم · مستحق النهارده · تنبيهات (رادار/نواقص/موعِدات) · أزرار لمسة واحدة** («سجلت فلوس» / «قفل الدرج» / «النواقص»).
- كل رقم يقفز للشاشة المصغرة (deep-link). حالة أول يوم = CTA «ابدأ أول عملية» (مش فضاء).

### 5.6 باقي الشاشات (بوليش عميق)
- **حالات ثلاثية إلزامية لكل شاشة** (تحميل skeleton / فراغ عربي + CTA / خطأ + إعادة) — بوابة `screens` (64/64) لا تغلق بدونها.

### 5.7 أداء الواجهة (مقاس، لا ادعاء)
- **LCP < 2s · CLS ≈ 0 · INP < 200ms** على 390px (يُقاس بـ Chromium script يُضاف لـ CI — lab data، لا RUM).

### 5.8 إكسسibilitي
