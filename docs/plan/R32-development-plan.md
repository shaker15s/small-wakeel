# خطة تطوير وكيل — R32 وما بعدها

**التاريخ:** 17 أكتوبر 2026 · **الفرع:** `arena/467cdeff-small-wakeel`
**المرجع الاستراتيجي:** `docs/research/wakil_200_year_evolution_blueprint_ar.md`

هذه ليست خطة نوايا. كل بند هنا خرج من **تجربة فعلية كصاحب بيزنس** على الأنشطة
الأربعة (سوبر ماركت، جيم، صيدلية، عطارة)، وكل معيار قبول مربوط بأمر واحد يمكن
تشغيله (`bun run sweep` / `bun run screens` / `bun run accept` / `bash scripts/ci.sh`).

---

## 1) كيف اتجرّبت المنصة (المنهج)

| الأداة | ماذا تفعل | لماذا هي دليل |
|---|---|---|
| `bun run sweep` | ٤١ سيناريو يوم شغل حقيقي على ٤ أنشطة عبر `POST /api/chat` الحقيقي (SSE)، بأدوار مختلفة (صاحب/كاشير) | تحكم على **الرد والكارت والأرقام والزمن** مش على الكود |
| `bun run screens` | ترسم الـ٨ شاشات فعليًا (SSR) لكل نشاط: **بيانات حقيقية + أول يوم + الشبكة واقعة** | تكشف «شاشة بايضة» و«الرقم غلط» بدون متصفح |
| `bun run accept` | رحلة «ضيف أحمد من اللي عليهم فلوس وعليه ٤٥٠ من أيام ١٠ أكتوبر» كاملة ثم تنظّف نفسها | تعديل المشروع من الشات، مثبت بالداتا |
| `bun run smoke` | ٨٨ نداء API | عقد الواجهات |
| `bun run evals` | ١٠ جمل عربية ذهبية | عدم انحدار الرد |
| `bun test` | ١٧٨ اختبار (وحدة + تكامل على نسخة مؤقتة من الداتابيز) | السلوك الداخلي |
| `bash scripts/ci.sh` | البوابة كلها بالترتيب | لا شيء يُشحن قبلها |

**قاعدة الحكم:** أي عيب يظهر للمالك لازم يتحول إلى **اختبار دائم** قبل إغلاقه.

## 3) ما زال مفتوحًا — ولماذا لم يُغلق بعد

| # | البند | لماذا هو مهم | لماذا لم يُغلق |
|---|---|---|---|
| A | **انقطاع الشبكة وسط الرد** | المالك بيكتب طلب، النت يقطع، مش عارف العملية اتسجلت ولا لأ | محتاج محاكاة قطع SSE في المتصفح + قرار «إعادة المحاولة الآمنة» (idempotency موجودة) |
| B | **المساعد الأول (Morning Brief)** | «مش مساعد كفاية»: عايز حد يبدأ يومه بقرار جاهز، لا ينتظر سؤال | تصميم بطاقة «ابدأ يومك» بثلاث توصيات قابلة للتنفيذ بضغطة |
| C | **الحركة/التصميم في الإحصاءات** | الرسوم لا تُرسم على السيرفر (recharts)؛ على الموبايل بطيئة أحيانًا | يحتاج قياس في متصفح حقيقي (LCP/INP) — البيئة هنا بلا متصفح |
| D | **اختيار الأداة عبر الموديلات الضعيفة** | بعض المزودين يختارون أداة القراءة الخطأ | عندنا الآن رجوع تلقائي للّادر عند فشل أداة كتابة؛ المتبقي: حظر أدوات الكتابة لسؤال صريح قبل تنفيذها |
| E | **صحة المزودين خارج الـprobe** | مزود بيرجع 200 وبعدها يفشل مع الأدوات | يحتاج telemetry تراكمي (نسبة فشل لكل موديل من `usage`) |
| F | **الأسعار القديمة في التقييم** | `price_anomaly` يعتمد على آخر عمليات؛ محل جديد = لا تاريخ | يحتاج fallback على `costPrice` + هامش القطاع |

## 4) الخطة — ثلاث مراحل، كل مرحلة قابلة للقياس

### المرحلة P0 — «الثقة» (الشبكة + عدم التكرار + الصدق)
**الهدف:** المالك ما يشكّش أبدًا: كل عملية معروفة الحالة، وكل فشل مقروء.

1. **SSE قابل للاستئناف**
   - كل رسالة لها `messageId` من أول `start`.
   - عند قطع الاتصال: زر «كمّل» يعيد طلب *نفس* الرسالة بـ`idempotencyKey` نفسه، والسيرفر يرجّع النتيجة المخزنة بدل إنشاء مسودة تانية.
   - شارة «الاتصال اتقطع — الرد ممكن يكون ناقص» في فقاعة الرسالة.
   - **قبول:** اختبار تكاملي يقطع الـstream بعد أول `delta` ثم يعيد الطلب → **مسودة واحدة** في الداتابيز.

2. **حظر أداة الكتابة على سؤال صريح**
   - قبل أي `prepare_draft`، لو النص سؤال خالص (يبدأ بـ«مين/ايه/كام/فين»، أو ينتهي بـ«؟»، ومفيهوش فعل أمر) → الأداة تُرفض ويُعاد التوجيه لأداة قراءة.
   - **قبول:** ٦ جمل أسئلة × ٤ أنشطة في الـsweep: صفر مسودات.

3. **لوحة «حالة النظام» للمالك**
   - في الإعدادات: آخر فحص لكل مزود، أبطأ أداة، نسبة الفشل آخر ٢٤ ساعة (من `/api/usage`).
   - **قبول:** الشاشة تعرض بيانات حقيقية (تُقاس في `screens`).

### المرحلة P1 — «المساعد الأول»
**الهدف:** يبدأ المالك يومه من غير ما يسأل.

4. **«ابدأ يومك» في اليوم + في الشات**
   - ثلاث توصيات مرتّبة بالأثر المالي، كل واحدة زر تنفيذ (مسودة جاهزة): «حصّل من أم حسن ١٢٥»، «اطلب ٦ أصناف نواقص»، «راجع ٣ مسودات قديمة».
   - مصدرها deterministic (مش LLM) = سريع ومجاني وثابت.
   - **قبول:** كل توصية لها زر ينشئ مسودة، والرقم فيها مطابق للـAPI (اختبار في `screens` + `sweep`).

5. **ملخص أسبوعي تلقائي**
   - كل يوم أحد ٩ صباحًا: رسالة واحدة فيها ٣ أرقام + قرار مقترح لكل رقم.
   - **قبول:** مهمة مجدولة تنفّذ وتظهر في الشات (اختبار زمني قابل للتشغيل الآن).

### المرحلة P2 — «الإتقان»
**الهدف:** إحساس منتج من الطبقة الأولى.

6. **الحركة والصوت البصري**
   - انتقالات الشاشات 200ms، Skeletons بدل وميض، `prefers-reduced-motion` محترم.
   - **قبول:** `motion-guard` test يمر + عدم وجود layout shift في SSR (قياس `screens`).

7. **الأداء**
   - ميزانية: P95 لأي سؤال بيانات < ٩٠٠ms محليًا، والرد الكامل < ٢.٥s.
   - **قبول:** `sweep` يطبع P95 ويفشل لو تجاوز الميزانية.

8. **التأمل (تقييم ذاتي)**
   - كل مسودة R3 لازم تحمل سبب الاعتماد + ملاحظة «تأمل» مرئية.
   - **قبول:** مغطى الآن باختبار؛ يمتد ليشمل كل `danger`.
