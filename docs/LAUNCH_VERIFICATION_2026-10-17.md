## الخلاصة

تم التحقق من أهم نتائج التقرير وتشغيل المشروع، ثم إصلاح مجموعة P0 الأساسية: منع الربط الخارجي الوهمي، إغلاق مسارات مكشوفة، إضافة هوية pilot مرتبطة بالمستخدم والمنشأة في الإنتاج، حماية اتصالات المزوّدين والويبهوكس، تشفير مفاتيح المزوّدين، وتفعيل workflow وبوابات جودة قابلة للتشغيل. ثم نُفّذت مرحلة ثانية لصلاحيات الكتابة الحساسة، وعزل دوال التنفيذ المالي، وذرية الحركات والعكس، واختبارات مالية عبر HTTP على بناء إنتاج فعلي.

**القرار يبقى NO-GO للإطلاق العام المدفوع أو تسليم النظام أموالًا وسجلات حقيقية بلا إشراف.** نجاح الاختبارات المحلية لا يغطي منظومة دخول SaaS كاملة، أو كل مصفوفة RBAC، أو تكاملًا خارجيًا حقيقيًا، أو تشغيل قاعدة/مهام الإنتاج.

## 2. الإصلاحات المنفذة

### أ. الحقيقة في الربط الخارجي

- `bridgeApplicationWithCliAnything` و`executeBridgedTool` يرجعان فشلًا صريحًا `not_connected` حتى يوجد adapter حقيقي مختبر؛ endpoint يعيده HTTP 409.
- حذف الأرقام المصطنعة، والمطابقة الزائفة، وfallback لسجل وكيل بوصفه بيانات برنامج خارجي.
- عدم توليد capabilities أو تسجيل plugin جديد يوهم باتصال حي.
- منع تشغيل plugins القديمة `app_cli_` قبل خطوات pipeline، بما في ذلك نقطة تنفيذ BasePlugin.
- تعطيل فحص ملفات/عمليات السيرفر في الإنتاج؛ ملفات تعريف التطبيقات في التطوير لا تعلن `hasCliHarness: true` بلا إثبات.

**هذا تعطيل آمن للادعاء غير المثبت، وليس تنفيذ connector.** قراءة Excel/POS وكتابة sandbox وread-back E2E تظل غير منجزة.

### ب. هوية وصلاحيات pilot

- الإنتاج يرفض الطلبات دون `WAKIL_AUTH_CREDENTIALS` سليمة؛ `WAKIL_ACCESS_TOKEN` المشترك لا يتجاوز ذلك.
- credential عشوائي منفصل لكل مستخدم، SHA-256 محفوظ في إعدادات السيرفر، ومستخدم/منشأة يُستخرجان من DB بكل طلب.
- منع انتحال `userId/businessId`، بما فيه headers المخالفة للقيم المرسلة من handler.
- bootstrap مقيد بالمستخدم والمنشأة المصادق عليهما.
- إدارة المزوّدين، health العام، global tick، provisioning وتشخيص السيرفر أصبحت لمدير النشر المعيّن صراحة.
- إغلاق `GET /api/providers` وقراءة تفاصيل العملية؛ تفاصيل عملية منشأة أخرى ترجع 404.
- تقييد تعديل/حذف الذاكرة والـplugins بمنشأة السجل نفسها، ورفض conversationId خارج المنشأة/المستخدم عند إنشاء مهام، مع دفاع إضافي في محرك الخلفية ومسارات التسليم. اختبارات تثبت بقاء السجلات الأجنبية بلا تغيير وعدم إنشاء عمل/رسائل في المحادثة الأجنبية.
- اختبار بنيوي لكل HTTP handler، مع اختبارات تنفيذية لرفض الانتحال والصلاحيات.
- شاشة دخول/فشل اتصال بدل spinner بلا نهاية. المفتاح في إنتاج المتصفح محفوظ في sessionStorage للتبويب فقط؛ bootstrap لا يرسل actor headers قديمة، ثم تتزامن واجهة المستخدم مع الهوية الراجعة.

**حدود:** هذا credential-based pilot وليس OAuth/OIDC أو منظومة جلسات/MFA/استرداد حساب. Provider registry لا يزال موردًا عامًا يديره مدير النشر، وليس BYO secrets مستقلة لكل tenant. المرحلة الثانية أدناه تغلق شريحة الكتابات الحساسة ومنها import/restore؛ ما زالت المصفوفة الكاملة لكل قراءة/كتابة وكل endpoint/tool، وتجربة الواجهة حسب الدور، غير معتمدة كمنظومة SaaS مكتملة.

### ج. حماية الشبكة والمفاتيح

- transport موحد مبني على Undici للمزوّدين في الإنشاء، probe، completion وstreaming، وللويبهوكس.
- HTTPS عام فقط، منع IPs غير العامة بما فيها IPv4-mapped IPv6، والتحقق من جميع نتائج DNS في socket lookup نفسه بدل فحص ثم resolution آخر.
- رفض redirects؛ provider URLs بلا credentials/query/fragment.
- `ALLOW_LOCAL_WEBHOOKS` لا يفتح الشبكة الداخلية في الإنتاج. لا bypass محلي للمزوّدين أو mock داخلي.
- AES-256-GCM لمفاتيح providers، بمفتاح خارجي `WAKIL_SECRETS_KEY`. الإنتاج يرفض plaintext legacy عند الاستخدام، مع أمر migration/rotation offline، dry run، وتحديث ذري.
- تحديث configs الموديلات داخل transaction بدل delete/create غير ذريين.

**حدود:** اختبارات الشبكة محلية للسياسة وDNS المحقون، وليست اختبار hostile network حي. محاولة transport إلى GitHub العام توقفت عند التحقق من شهادة TLS (`UNABLE_TO_VERIFY_LEAF_SIGNATURE`) في هذه البيئة؛ لم نعطل TLS verification ولم ندّع اتصال provider ناجح. لم تُرحّل أو تُدوّر أي مفاتيح إنتاج فعلية، ولا ندّعي اكتمال مراجعة redaction لكل logs/SDK.

### د. CI والبناء وتشغيل القاعدة

- إضافة `.github/workflows/ci.yml` فعلي، وتوحيده مع نسخة `docs/ci`، وصلاحيات workflow للقراءة فقط ورفع log باسم SHA.
- توحيد scripts، تثبيت Bun 1.3.11/Prisma 6.19.3، إضافة dependency parser الناقصة، ونجاح frozen install.
- إعادة استخدام مولد Prisma engine-free في postinstall وdb:generate دون الاعتماد على `npx` أو تنزيل Rust engines.
- إصلاح `await` الناقصة، وعدم تنزيل Google fonts غير المستخدمة.
- lint يغطي كود التطبيق ويستبعد `cli-anything/**` المورّد؛ **لم نصلح أو نراجع كود ذلك المشروع خارجيًا**. بقيت 48 تحذيرًا غير مانعة.
- أمر snapshot ثابت باستخدام `VACUUM INTO`، وdrill آلي للاستعادة على نسخة synthetic يفحص integrity/foreign keys/schema/counts/cash/stock.
- production smoke يقلع نسختين حقيقيتين من البناء على DB مؤقتة: إنتاج بلا إعدادات هوية، ثم إنتاج بهويات pilot. يفحص رفض الوصول، عزل المنشآت، bootstrap، health، HTML RTL، ورفض bridge.
- تدقيق 8 شاشات × 3 حالات = **24 حالة render** على بيانات منشأة synthetic واحدة ضمن الهوية المصادق عليها. **ليس اختبارًا في متصفح** ولا تدقيقًا لكل المنشآت.
- تحديث Docker/Compose للنسخ والتثبيت المجمد ومتطلبات الهوية/المفتاح وhealth المصادق عليه؛ حذف خدمة mock غير المدعومة. لم يتوفر Docker لتشغيل container فعلي هنا.

### هـ. المرحلة الثانية: الصلاحيات وسلامة التنفيذ المالي

**هذه مرحلة تنفيذ إضافية بعد التسليم الأول، وليست إعادة صياغة للوثيقة فقط.** انتقل إجمالي الاختبارات من 269 إلى **306**، مع ثلاثة ملفات اختبار جديدة وHTTP مالي فعلي داخل بوابة الإنتاج.

#### شريحة الصلاحيات المنفذة

- **المالك فقط:** تنزيل full JSON export بما فيه السجل المالي وaudit.
- **المالك أو المشرف:** استيراد/استعادة الكتالوج، إدارة وقراءة إعدادات الأدوات، تركيب/تعديل plugins، تعديل الذاكرة والتعلّم الضمني للقواعد، جدولة/إرسال المهام الخلفية، إعدادات المنشأة والنبرة المشتركة.
- أدوات domain/agent الرئيسية تعيد فحص الفاعل، ولا تعتمد على إخفاء الزر أو تعليمات الموديل. enqueue وdispatch وبدء worker تفحص الصلاحية؛ helper الكتالوج يتطلب userId صريحًا.
- middleware لا يختلق `role: owner`، وتشغيل starter plugin للقراءة لا يثبّته خلسة باسم أول مستخدم/المالك.
- ملاحظات scratchpad مقيدة بصاحب المحادثة، حتى داخل نفس المنشأة. الموظف يمكنه استخدام أمر سريع مشترك، لا إعادة كتابة/حذف أمر مستخدم آخر بلا صلاحية إدارة.
- `WAKIL_STRICT_APPROVALS=1` يعني **اعتماد الإدارة فقط**، وليس four-eyes segregation: المالك/المشرف يمكنه اعتماد مسودته. صاحب المسودة يمكنه إلغاء مسودته المسموحة التي ما زالت معلقة.

**حدود الشريحة:** قراءات التقارير والكتالوج التشغيلية ما زالت مشتركة داخل المنشأة. لم نعتمد field-level read grants أو كل مسارات الكتابة الداخلية أو واجهة مخصصة لكل دور. سياسة الذاكرة الحالية تحفظية وتقيّد الحفظ الصريح للمالك/المشرف، وليست تصميمًا نهائيًا لتفضيلات الموظف الشخصية.

#### دليل الاختبار المالي

- `tests/integration/financial-integrity.test.ts`: عضوية/أدوار ومراجع مالية، idempotency متزامن، risk floor، approve/cancel، منافسة عمليتين على نفس المخزون، عكس متزامن، عكس بيع/شراء/مصروف/تحصيل/سداد، وfault injection عند audit/cash/read-back.
- `tests/integration/role-boundaries.test.ts` و`tests/unit/permissions.test.ts`: رفض الموظف داخل نفس المنشأة، نجاح المسارات المسموحة، تغيّر الدور من DB، سياسة strict الصحيحة، خصوصية الملاحظات والأوامر المشتركة، ومنع التثبيت/التعلّم/المهام عبر الاستدعاء المباشر.
- `scripts/financial-http-smoke.ts` يستدعيه production smoke: **38 طلب HTTP إضافيًا** على server إنتاج حقيقي وDB مؤقتة، لتسعة أنواع حركة مالية مع رفض/تكرار/سباق/rollback. أغلبها يستخدم مسودات fixture صريحة، وليس استخراج كل نوع من المحادثة.
- مسار مصروف عربي واحد كامل: chat/SSE → مسودة محفوظة بلا أثر مالي → اعتماد → إعادة نفس الدور بعد اكتماله دون مسودة/حركة ثانية، في وضع **offline**.
- أخطاء Prisma الظاهرة عند fault injection متعمدة لإثبات التراجع وليست فشل بوابة. أول محاولة HTTP كشفت افتراضًا خاطئًا في fixture عن إنشاء محادثة جديدة؛ عُزلت محادثة الاختبار ثم نجحت إعادة التشغيل والبوابة كاملة.

**لم يُختبر هنا:** متصفح حقيقي، قطع SSE عمدًا أثناء الكتابة، قتل process وسط المعاملة، أو حجم/تزامن نشر فعلي. الحجز الأولي منفصل عن معاملة الآثار؛ تعطل process/storage قد يترك EXECUTING بلا reconciler تلقائي. لا تُعاد مثل هذه العملية عميانيًا، ولا تُطبّق ضمانات الكود الجديد بأثر رجعي على عمليات قديمة ذات أثر جزئي مجهول.

## 5. ترتيب التنفيذ التالي وحدود الاعتماد الخارجي

1. **هوية SaaS:** اعتماد مزود وطريقة تسجيل/دعوات/استرداد/سياسة أدوار وجلسات، ثم تنفيذ session lifecycle وربط DB الحالي. لم نفترض مزودًا أو ننشئ بنية إنتاج أو ننقل سجلات حقيقية تلقائيًا.
2. **Financial browser/recovery:** استخدام staging اصطناعي، إضافة اختبار متصفح مع قطع الشبكة وقت الحفظ، واختبار فقد process وإجراء reconciler مع دليل عدم تكرار الأثر. نجاح replay لدور مكتمل لا يغطي هذه الحالات.
3. **Hosted CI:** نشر الفرع ومراجعة run على SHA محدد وإعداد required check بصلاحية مناسبة. خطأ Checks API السابق لا يبرهن اكتمال هذه الخطوة؛ لا نسجلها منجزة محليًا.
4. **معمارية النشر والاستعادة:** اختيار عقد single-process/persistent volume أو خطة انتقال DB/queue، ثم drill off-host بمفاتيح وحجم حقيقيين، لا الاعتماد على زمن synthetic.
5. **Connector:** اختيار نظام خارجي وحساب sandbox وعقد صلاحيات ومصدر بيانات قابل للتحقق؛ يبدأ read-only، ثم كتابة تجريبية وread-back. يبقى المسار الحالي fail-closed حتى ذلك.

**الحالة عند نهاية هذه المرحلة:** الإصلاحات والاختبارات محفوظة على فرع العمل المحلي؛ الإطلاق العام المدفوع ما زال **NO-GO**، وليس هناك ادعاء بإغلاق الوثيقة كلها.
